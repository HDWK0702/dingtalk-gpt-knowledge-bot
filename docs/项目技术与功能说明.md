# 企业知识库智能问答机器人：技术与功能说明

## 1. 项目概述

本项目是一套面向企业内部员工的知识库智能问答机器人。员工可以直接在钉钉中提问，系统从企业已有的 Obsidian Markdown 资料中检索相关内容，再交给大语言模型整理答案，最后通过钉钉回复员工。

项目目前已经完成从“钉钉提问”到“知识库检索、模型回答、钉钉回复、日志记录”的基础闭环。

## 2. 当前运行流程

```text
员工在钉钉中提问
  ↓
钉钉 Stream 将消息发送给 Python 程序
  ↓
程序检查消息并初步判断问题所属业务类型
  ↓
Embedding 服务把问题转换成向量
  ↓
系统在本地向量索引中查找相似的文档 Chunk
  ↓
把“员工问题 + 检索资料”发送给大语言模型
  ↓
大语言模型根据资料生成答案
  ↓
程序补充资料来源并通过钉钉回复
  ↓
保存问题、调用线路、响应时间和首要文档等日志
```

## 3. 使用的技术

### 3.1 Python

Python 是整个项目的主要开发语言，用于连接钉钉、读取知识库、调用 Embedding、检索资料、调用大语言模型以及记录日志。

实际效果：把各个独立服务串成一条完整的自动问答流程。

### 3.2 钉钉 Stream 机器人

钉钉 Stream 用于建立机器人程序与钉钉之间的长连接。员工发送消息后，机器人可以实时收到消息，并把生成的答案回复到钉钉。

实际效果：员工不需要打开新的系统或网页，在日常使用的钉钉中就能查询企业资料。

### 3.3 Obsidian 与 Markdown

Obsidian 是当前知识资料的维护工具，Markdown 文件是知识库的主要文件格式。管理员可以像编辑普通笔记一样修改制度、培训手册和产品问答。

实际效果：知识资料便于阅读、修改、分类和版本管理，不需要先开发复杂的知识库后台。

### 3.4 MarkItDown

MarkItDown 用于把 Word 文档转换为 Markdown 文件。

实际效果：原有的 Word 培训资料可以更方便地进入 Obsidian，并参与后续的文档切分和检索。

### 3.5 Chunk 文档切分

Chunk 是把一份长文档切成多个有完整含义的小段。当前切分程序会优先按照 Markdown 标题、段落、句子等结构处理，并保留标题层级、来源路径和 Chunk ID。

实际效果：系统不必把整本手册一次性交给模型，而是只取与问题最相关的几个片段，减少无关内容并提高检索准确度。

### 3.6 Embedding

Embedding 服务负责把文档片段和员工问题转换成一组数字，也就是向量。这组数字用于表达文本的大致含义。

实际效果：即使员工提问时没有使用文档中的原词，只要意思相近，系统也有机会找到对应资料。

### 3.7 本地向量索引与相似度检索

文档 Chunk 生成向量后，当前保存在本地 `rag_index.json` 索引中。员工提问时，程序计算问题向量与文档向量之间的相似程度，并选出最相关的资料。

实际效果：实现“按意思查资料”，而不只是简单匹配关键词。

说明：当前使用的是本地索引，还没有迁移到 PostgreSQL 与 pgvector。

### 3.8 RAG 检索增强生成

RAG 的工作方式是“先检索资料，再让模型回答”。大语言模型收到的不只是员工的问题，还包括系统检索出的企业资料。

实际效果：模型回答更贴近企业自己的制度和业务内容；没有相关资料时，系统可以拒绝回答，降低模型凭空编造的风险。

### 3.9 大语言模型 API

大语言模型负责阅读检索到的资料，并把资料整理成自然、简洁的中文答案。它不负责存放企业资料，也不应代替知识库检索。

当前支持两种调用方式：

- 主线路使用 Responses API。
- 备用线路使用 Chat Completions API。

实际效果：主线路出现超时、限流或网络故障时，可以切换到备用线路，提高问答服务的可用性。

### 3.10 FastAPI

FastAPI 为程序提供网络接口。当前包括健康检查接口和内部检索接口，可供后续监控、管理后台或其他企业系统调用。

实际效果：知识库能力不再只能由钉钉机器人使用，后续还可以接入网页、企业应用或自动化流程。

### 3.11 问答日志与用户反馈

系统会保存机器可读的 JSONL 日志和便于管理员查看的 Markdown 日志。日志可以记录提问人员、问题、调用线路、响应时间、命中文档、错误和反馈。

员工可以提交“有用”或“没用”的评价。

实际效果：管理员可以分析员工经常问什么、哪些问题没有资料、哪条模型线路较慢，以及哪些回答需要继续优化。

### 3.12 Redis

项目已经安装 Redis 的 Python 客户端，并写入了钉钉消息去重代码。设计上，Redis 会记录已经处理过的消息 ID，防止钉钉重发消息时机器人重复回答。

当前状态：代码和配置已经存在，但 Docker 引擎尚未正常启动，因此 Redis 服务还没有完成实际运行验证。

### 3.13 Docker 与 Docker Compose

Docker 用于把 Python 程序、运行环境和依赖打包成容器；Docker Compose 用于统一启动机器人、FastAPI 和 Redis。

实际效果：环境调通后，可以减少“换一台电脑就运行不了”的问题，也方便后续部署到云服务器。

当前状态：项目已经有 Dockerfile 和 Docker Compose 配置，但本机 Docker Engine 仍在排查，不能写成已经部署成功。

### 3.14 Git

Git 用于保存代码的历史版本，记录每次修改，并在出现问题时与以前能运行的版本进行对比。

实际效果：后续修改检索、日志或模型代码时，有清晰的版本记录，不需要依靠复制很多文件夹来备份。

### 3.15 uv 与 Python 虚拟环境

uv 用于创建项目虚拟环境、安装依赖和运行 Python 程序。`.venv` 是该项目独立使用的 Python 环境。

实际效果：项目依赖不会与电脑上其他 Python 项目互相干扰，安装和启动命令也更统一。

### 3.16 pytest

pytest 用于运行自动化测试，检查文档切分、知识检索、日志和模型线路等代码在修改后是否仍然正常。

实际效果：每次改代码后可以快速发现旧功能是否被意外破坏。

### 3.17 Windows BAT 启动脚本

项目提供了机器人启动、重新 Chunk、重建索引和 Word 转 Markdown 等 BAT 文件。

实际效果：常用操作可以通过双击执行，不需要每次手动输入完整命令。

## 4. 已实现的主要功能

### 4.1 钉钉实时问答

- 接收钉钉员工发送的问题。
- 调用知识库和大语言模型生成答案。
- 将最终答案回复给员工。

### 4.2 文档导入和处理

- 支持读取 Obsidian 中的 Markdown 文件。
- 支持把 Word 转换成 Markdown。
- 支持根据标题和段落切分长文档。
- 保留文档标题、章节、来源和 Chunk ID。
- 支持排除草稿、归档或不参与检索的资料。

### 4.3 语义检索

- 把文档和问题转换成向量。
- 从向量索引中选出相似资料。
- 支持设置返回资料的数量。
- 没有可靠资料时返回拒答提示。

### 4.4 业务类型初步判断

- 可以通过显式前缀或关键词初步区分“财法通产品”和“内部业务培训”。
- 无法判断时，可以提示员工选择业务类型。
- 支持结合最近几轮对话判断追问所属的业务类型。

当前限制：业务标签和知识库隔离还需要继续整理，因此仍可能发生不同资料之间的错误混用。

### 4.5 模型双线路故障转移

- 优先调用主模型。
- 主模型出现可重试的超时、限流或网络错误时，调用备用模型。
- 日志记录实际使用的线路和模型。
- 两条线路都失败时，返回服务暂不可用提示。

### 4.6 答案来源与拒答

- 回答后展示实际使用的资料名称。
- 不允许模型自行编造来源。
- 找不到有关资料时明确告诉员工知识库暂无可核实答案。

### 4.7 日志和反馈

- 保存收到的问题和生成的答案。
- 保存提问人员、响应时间、模型线路和命中文档。
- 保存程序错误，便于排查故障。
- 接收员工“有用”和“没用”反馈。

### 4.8 健康检查和内部检索接口

- `/health` 用于确认 FastAPI 服务是否存活。
- `/internal/search` 用于让经过授权的内部程序调用知识检索。

## 5. 当前取得的效果

- 已经跑通钉钉提问、知识库检索、大模型回答和钉钉回复的完整流程。
- 长文档能够先按结构切分，再进行向量化检索。
- 员工使用不同说法提问时，系统可以通过语义相似度寻找资料。
- 模型只能基于检索资料回答，资料不足时会拒答或提示人工确认。
- 主模型故障时具备切换备用模型的能力。
- 管理员能够通过日志分析问题、响应速度、调用线路和引用资料。
- 常用操作已有 BAT 脚本，降低了日常启动和维护难度。
